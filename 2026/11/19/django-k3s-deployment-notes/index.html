Django 部署排错：从 PostgreSQL 到 GHCR 和 K3s

Nianer 发布于 2026-11-19

  • 🏷️ Docker
  • 🏷️ 部署

这次练习用 Docker Compose 在本地运行 Django 和 PostgreSQL，再通过 GitHub Actions 构建镜像、推送到 GHCR，并尝试部署到 K3s。镜像最终推送成功，自动部署停在 Runner 连接 Kubernetes API 的阶段。以下记录每一步的故障现象和验证方法。

PostgreSQL 已经起来，Django 怎么还在用 SQLite？

Compose 里的 PostgreSQL 已通过 pg_isready，直接连库也能执行查询。本项目以 SQLite 为默认后端，只有五项 PostgreSQL 连接配置都有值时才会启用 PostgreSQL。此次 Django 进程未能读取数据库密码，因此继续使用 SQLite。在与 Web 进程使用相同配置的 Django shell 里执行下面两行，可以直接确认实际使用的数据库后端。

from django.db import connection

print(connection.vendor)  # postgresql 或 sqlite

管理员登录也需要核对实际使用的数据库。migrate 会更新当前数据库的表结构，管理员账号需要另外创建。在 SQLite 创建的用户不会出现在 PostgreSQL 里。先确认数据库后端，再检查账号是否已启用并具备 Admin 登录所需的 staff 身份。

Compose 的端口也有两层。以 5434:5432 为例，宿主机通过 5434 访问 PostgreSQL，同一 Compose 网络中的 Django 则通过服务名和容器端口访问，例如 postgres:5432。如果用 -p 5434 修改了 PostgreSQL 自身的监听端口，容器之间的连接配置也要随之修改。

Admin 能打开，样式却全是 404

Gunicorn 下登录页能返回 200，但 Admin 的 CSS 和 JavaScript 一开始全是 404。这次在 Django 里设置了 STATIC_ROOT，把 WhiteNoise 中间件放在 SecurityMiddleware 之后，并在启动 Gunicorn 前运行 collectstatic。

python manage.py collectstatic --noinput

collectstatic 把资源汇总到 STATIC_ROOT，WhiteNoise 负责响应静态资源请求。修改后抽查了五个 Admin CSS 和 JavaScript 地址，均返回 200。排查时可以直接请求 /static/admin/css/base.css，把静态资源问题和登录表单问题分开验证。

镜像构建成功，为什么 push 还报 403？

第一轮构建成功，GHCR 登录也成功，但上传镜像层时返回了 403 Forbidden。工作流的 GITHUB_TOKEN 已有 packages: write，还需要在已有镜像包的 Package settings → Manage Actions access 中给工作流所在仓库写权限。调整权限后，重跑成功推送了镜像。

Runner 上的 127.0.0.1 是谁？

镜像推上去后，工作流在更新 Kubernetes Secret 时遇到下一条错误。

dial tcp 127.0.0.1:6443: connect: connection refused

本地 kubeconfig 指向 https://127.0.0.1:6443，因为我的 Windows 机器用 SSH 隧道转发了这个端口。把配置放进 GitHub Actions 的 K3S_KUBECONFIG 后，同一个地址就指向 Runner 自己。Runner 上没有对应隧道，连接随即被拒绝。

接下来在 Windows 上预检 K3s API 的公网可达性。我在服务器上用 ss -lntp 'sport = :6443' 确认 K3s 正在监听，但 Windows 测试时，ping 有响应，TcpTestSucceeded 仍然是 False。K3s API 自带 HTTPS，这次连接还没走到 TLS 证书验证。

下一步是用服务器端抓包确认连接请求是否到达，同时在客户端重测端口。将示例域名换成自己的 API 地址。

sudo tcpdump -ni any 'tcp port 6443'

Test-NetConnection k3s.example.com -Port 6443

如果抓不到客户端的 SYN，可以先查云安全组、来源 IP 范围和网络路径。如果看到了 SYN，却没有 SYN-ACK，再查本机过滤规则和监听状态。若服务器发出了 SYN-ACK 而客户端仍连接失败，可以继续检查回程路径。TCP 打通后，用实际部署环境的 kubeconfig 验证 API 访问，保留 CA 校验。如果收到明确的证书名称不匹配错误，再检查 K3s 的 tls-san 配置。

这次实际跑通了本地 Admin 静态资源和 GHCR 镜像推送。自动部署停在连接 K3s API，后面的滚动更新和数据库迁移在这轮 Actions 里还没有执行。
