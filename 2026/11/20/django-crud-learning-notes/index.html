Django CRUD 学习笔记：从 ORM 到文章管理页面

Nianer 发布于 2026-11-20

这次我在现有的 Django 项目里新建了一个 articles 应用，练习管理文章。顺序是先迁移数据库，再用 Shell 做一遍增删改查，最后让浏览器发出的请求走同样的流程。这篇接着上一篇部署学习笔记，重点回到 Django 应用本身。

先建表，再在 Shell 验证数据

django_k8s 项目负责全局配置和入口路由，articles 应用负责文章业务。我用 python manage.py startapp articles 创建应用，在 INSTALLED_APPS 注册 articles.apps.ArticlesConfig，再定义模型。标题用最长 200 字符的 CharField，正文用 TextField，创建时间由 DateTimeField(auto_now_add=True) 填入。Django 自动提供主键，后面的查询和编辑路由都用它定位文章。

python manage.py makemigrations articles
python manage.py migrate
python manage.py showmigrations articles

看到 [X] 0001_initial 后，我进入 Django Shell 验证模型。练习更新时最直观的一步是先改 Python 对象，再从数据库查一次，观察调用 save() 前后的差异。

from articles.models import Article

draft = Article.objects.create(title="修改练习", content="初稿")
draft_id = draft.pk
draft.content = "修改后的正文"

print(Article.objects.get(pk=draft_id).content)  # 初稿
draft.save()
print(Article.objects.get(pk=draft_id).content)  # 修改后的正文

draft.delete()
print(Article.objects.filter(pk=draft_id).exists())  # False

给对象属性赋值只改变内存里的对象。save() 把变化写入数据库。get() 适合取一条明确的记录，记录不存在时会抛出异常。exists() 适合只检查记录是否还在。

把查询接到文章列表

项目路由用 path("articles/", include("articles.urls")) 匹配前缀，应用路由用空路径接住余下的部分。访问 /articles/ 时，Django 调用列表视图。视图把按创建时间倒序排列的查询集交给模板，时间相同时用主键打破平局。

def article_list(request):
    articles = Article.objects.order_by("-created_at", "-pk")
    return render(request, "articles/article_list.html", {"articles": articles})

模板循环输出标题和正文，用 {% empty %} 处理没有文章的情况。当浏览器里出现 Shell 中创建的三篇文章时，我就能把整条链路对上了：路由找到视图，视图准备数据，模板把它变成 HTML。

用 ModelForm 新增文章

ArticleForm 继承 ModelForm，显式允许编辑 title 和 content。字段类型和长度校验来自模型。访问 /articles/new/ 时，GET 显示空表单，POST 绑定用户输入。校验失败会带着输入和错误重新显示表单，成功则保存并重定向到列表。

def article_create(request):
    if request.method == "POST":
        form = ArticleForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect("article_list")
    else:
        form = ArticleForm()

    return render(request, "articles/article_form.html", {"form": form})

模板里的 POST 表单包含 {% csrf_token %}，入口链接通过路由名生成。保存后浏览器发起一次新的 GET，刷新列表时就只会重新查询。

这里遇到过一次列表模板错误。日志显示新增请求先返回 302，随后列表的 GET 才返回 500。沿着视图顺序看，保存已经执行，失败发生在重定向后的模板渲染。修复模板后，直接刷新列表就看到了已保存的文章。这次让我学会了把浏览器的一次操作拆成多条 HTTP 请求来看。

从 21 秒定位到 PostgreSQL 连接

列表可以打开以后，浏览器的 Network 面板还显示一次请求用了约 21 秒。随后把数据库建立连接和执行查询分开测量，结果如下。

测量项 会话中的实测
用 localhost 建立 PostgreSQL 连接 21.09 秒，期间 ::1 连接超时
改用 127.0.0.1 建立连接 约 32 毫秒
执行文章查询 约 6 毫秒
新进程中 Django 测试客户端首次请求列表 约 144 毫秒，返回 200

这套本地环境在尝试 IPv6 回环地址时耗掉了大部分时间。我把本地 POSTGRES_HOST 改为 127.0.0.1，让连接直接走 IPv4。144 毫秒来自重新加载配置后的 Django 测试客户端。已有的 runserver 需要重启后，再从浏览器复测。

编辑时让表单绑定已有文章

编辑路由用 <int:pk>/edit/ 把主键传给视图。视图先用 get_object_or_404(Article, pk=pk) 取记录，再复用新增用过的表单和模板。

  • GET 使用 ArticleForm(instance=article)，表单预填已有的标题和正文。
  • POST 使用 ArticleForm(request.POST, instance=article)，通过校验后更新同一条记录。
  • 模板从 page_title 判断显示“新增文章”还是“编辑文章”，表单提交到当前地址。

我在列表里点进一篇文章，确认表单显示的是它原来的内容。保存后核对同一篇文章发生变化，文章总数保持不变。这个验证可以抓到编辑 POST 漏传 instance 的问题，因为那会让 form.save() 新建一条记录。

删除分成确认和执行两步

删除沿用按主键取对象的方式。GET /articles/<pk>/delete/ 显示待删除文章的标题，用户可以取消。点击确认后，表单带着 CSRF 令牌向同一地址发送 POST，视图才调用 article.delete() 并重定向回列表。主键已经在 URL 里，表单无需再传一次。

练习的最后一步是用同一篇文章串起整个流程：新增后在列表里看到它，编辑后确认总数没变，进入删除确认页核对修改后的标题，取消时文章仍在，确认后列表只少这一篇。到这里，Shell 里的 ORM 操作已经接到了真实的网页请求上。
